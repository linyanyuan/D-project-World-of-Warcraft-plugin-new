## Goal

Build a **maintainable** external client that can fully auto-play **Unholy Death Knight** on WoW Retail/Midnight.

Stack: **PySide6 + dxcam** (+ mss / PrintWindow), OpenCV for buff templates, SendInput for keys.

This is a clean rewrite inspired by recovered Nirvana30 architecture, **not** a 1:1 decompile.

## Non-goals (v1)

- License/login/cloud cycle marketplace (**deferred**: see `docs/auth-cardkey-plan.md`)
- Full Fluent/qfluentwidgets visual clone
- All-class support
- Complete AutoPlayer Lua source recovery (parallel track)
- Shipping packed/protected binaries

### Deferred: card-key auth

Original Nirvana uses remote `prod-api` card-key / account login + heartbeat + remaining-time UI. Keys are generated by a backend admin, not the client. `clean_client` v1 is **login-free**; card-key support is planned later per `docs/auth-cardkey-plan.md`.

### Why Model A

Recovered Nirvana flow is:

`capture → parse header/HP/keybinds/CDs/buffs → match cycle pixel_keys → SendInput`

A separate rich local priority engine (Model B) would require a much denser state schema than we can trust yet and diverges from the working product. v1 follows Model A; a later optional “local Unholy arbiter” can sit above parsed actions.

`UnholyAssist` is only a **macro/spell-ID helper**, not a live condition engine. Reuse: action names / spell IDs / default keybind labels. Do not treat it as combat AI.

## Pixel protocol (source of truth)

See `_analysis/lua_deobf/PIXEL_PROTOCOL_RECOVERED.md` and `RGB_MARKERS.json`.

Summary:

1. Regions: `Skill`, `Target`, `Player`, `Buff` (files `*_region.txt`)
2. Skill region rows:
   - Row0 header (`_parse_header_rgb_protocol`)
   - Health bars
   - Key bindings (`ID -> key`, markers for spell/item/mod)
   - Cooldowns (bars + highlighted/usable)
3. Buff region: OpenCV template match (`buff_match_threshold`, default 0.7)
4. Spell id packing: `spell_id = (R<<16)|(G<<8)|B` (example `#12ca33` → `1231411`)
5. Markers: start `#ff00ff`, end `#ff8000`, sep `#808080`, spell `#ffffff`, item `#ffff00`, …

**Still missing for live accuracy:** exact region coordinates / texture anchors; full header field name map; some CD kind G/B dictionaries. v1 ships calibration + placeholder regions.

## Architecture

```text
clean_client/
  app.py
  ui/main_window.py
  capture/          # dxcam, mss, printwindow
  input/sendinput.py
  vision/           # pixel protocol parsers + buff matcher
  rotation/         # thin action selector over parsed pixel_keys (Unholy profile)
  config/
  models/           # CombatState, Action, regions
  tests/
```

### Engine loop / threading

- Worker `QThread` owns the tick loop (default `tick_ms=30`)
- UI thread only signals start/stop/config changes and appends logs via queued signals
- Stop = cooperative flag checked each tick; Pause = skip Input but keep Vision optional
- Foreground guard: if enabled and WoW not foreground → skip SendInput (still log in dry-run)

### Data flow

1. Capture frame (BGR `np.ndarray`, document backend channel order)
2. Vision parses protocol → `CombatState`
3. Rotation maps Unholy profile `pixel_keys` / allowed actions against parsed bindings & highlighted/ready skills → `Action | None`
4. Input presses key unless `dry_run`

## Shared schemas

```python
@dataclass
class Action:
    spell_id: int | None
    key: str                 # e.g. "1", "alt+2"
    kind: str                # spell|item|etc
    name: str | None = None

@dataclass
class CooldownInfo:
    spell_id: int
    unusable: bool
    has_cooldown: bool
    highlighted: bool
    cd_remain_s: float | None
    charge_count: int | None
    kind: str

@dataclass
class CombatState:
    header: dict[str, object]          # team_type, gcd, spec, bools...
    health: dict[str, dict]            # player/target/focus/...
    bindings: dict[int, Action]        # spell_id -> action
    cooldowns: dict[int, CooldownInfo]
    buffs: list[dict]                  # template matches
    pixel_keys: list[str]              # from active cycle profile
    raw_debug: dict[str, object]
```

Condition filters (optional Unholy profile JSON) may gate actions using highlighted/CD/header flags only—no invented rune math in v1 unless header exposes it.

## Module notes

### UI

Start/Stop, dry-run, capture mode (`方式一/二/三` mapped to backends), tick_ms, cd_ready_window_ms, buff_match_threshold, hotkey (F8), foreground guard, region calibration entry, log pane. Mode toggles displayed if header exposes them later.

### Capture

`CaptureBackend.grab() -> np.ndarray` in **BGR**. Map:

- 方式一 → PrintWindow (verify against live Nirvana later)
- 方式二 → mss
- 方式三 → dxcam

(Exact mapping adjustable once confirmed; keep aliases in config.)

### Vision

- `PixelProtocolVision` implementing row parsers using `RGB_MARKERS.json`
- Region load/save compatible with `skill_region.txt` etc.
- `MockVision` for tests
- Calibration helper to pick rectangles

### Rotation (thin)

Unholy profile JSON (spell_id is the join key to protocol bindings):

```json
{
  "name": "unholy_default",
  "prefer_highlighted": true,
  "actions": [
    {"spell_id": 77575, "name": "Outbreak", "kind": "spell", "fallback_key": "1"},
    {"spell_id": 85948, "name": "FesteringStrike", "kind": "spell", "fallback_key": "2"}
  ]
}
```

Legacy string `pixel_keys` are not used in v1.

**Ready predicate** for a `CooldownInfo` / binding candidate:

```text
near_ready = cd_remain_s is not None and cd_remain_s <= (cd_ready_window_ms / 1000)
ready = (not unusable) and ((not has_cooldown) or near_ready or highlighted)
```

**Selector algorithm:**

1. Walk profile `actions` in order.
2. Look up `spell_id` in `CombatState.bindings` (fallback: synthesize Action from `fallback_key` only in dry-run fixtures).
3. Look up matching `CombatState.cooldowns[spell_id]` if present.
4. Accept first action that is `ready`.
5. If `prefer_highlighted` is true, among ready candidates at the same priority walk, prefer one with `highlighted=true` when choosing between otherwise equal options (still first-accept in ordered walk: if an earlier ready non-highlighted action exists, it wins; highlighted only breaks ties when comparing simultaneously eligible entries — v1 simplifies to: skip non-highlighted while any later highlighted ready exists only if config `require_highlighted=true`; default false).

v1 practical rule (deterministic): **first profile action whose spell_id is ready** wins. `prefer_highlighted=true` means: first try a pass that only accepts `highlighted` ready actions; if none, second pass accepts any ready action.

### Input

SendInput tap with press duration; anti-spam: do not re-press same key within GCD/header gate or configured min interval.
